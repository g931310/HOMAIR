# Contributing to HOMAIR

Thank you for your interest in contributing to HOMAIR.

HOMAIR is an open-source reproducibility framework for explainable machine-learning research on insulin resistance and HOMA-IR prediction. Contributions that improve reproducibility, documentation, validation methodology, testing, and reusable research utilities are welcome.

## How to Contribute

### Report a Bug

Please open a GitHub Issue and include, when applicable:

* a clear description of the problem
* steps required to reproduce the issue
* the expected behavior
* the observed behavior
* Python version
* relevant package versions
* error messages or traceback information

Please do not include participant-level health data, confidential database information, credentials, or other restricted materials in an Issue.

### Suggest an Enhancement

Feature requests and methodological suggestions are welcome.

Examples include:

* additional validation utilities
* improved threshold-selection procedures
* statistical comparison tools
* reproducibility checks
* documentation improvements
* synthetic-data examples
* compatibility testing

Please open an Issue describing the proposed enhancement and its intended use.

### Submit a Pull Request

1. Fork the repository.
2. Create a new branch for your proposed change.
3. Make and test your changes.
4. Update documentation when appropriate.
5. Submit a pull request with a concise description of the changes.

Please keep pull requests focused on a specific change whenever possible.

## Contribution Scope

Contributions should focus on the public reproducibility framework.

Appropriate contributions may include:

* source-code improvements
* validation utilities
* testing infrastructure
* statistical evaluation tools
* documentation
* synthetic example workflows
* reproducibility enhancements

The following materials are outside the scope of the public repository:

* participant-level MJ Health Database data
* personally identifiable information
* proprietary database mappings
* confidential source-database documentation
* restricted research data
* access credentials
* private institutional files
* unpublished proprietary workflows

## Data and Privacy

Do not submit real participant-level health information or other restricted data through Issues, pull requests, discussions, or example files.

Synthetic or openly licensed example data should be used when demonstrating code behavior.

## Reproducibility

Contributions should, where applicable:

* avoid data leakage
* preserve separation between training and evaluation data
* document random seeds
* document major dependencies
* provide clear input and output expectations
* include sufficient information for independent reproduction

## Code and Documentation

Please keep code readable and reasonably documented.

For methodological changes, briefly explain:

* what was changed
* why the change is needed
* how the change was evaluated

Documentation-only contributions are also welcome.
